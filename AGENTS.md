# ntarlink engineering rules (English-only repository)

ntarlink aims to model a complete, reproducible, Starlink-like LEO broadband satellite internet system, not a reproduction of undisclosed SpaceX protocols.

## Language and organization

- **All committed repository content MUST be English**: documentation, headings, code comments, fixtures, commit/PR/issue descriptions generated by agents, UI copy, interface names and test descriptions. Do not add Chinese or other non-English prose to source-controlled artifacts without a documented protocol/data reason; Unicode in external data may be allowed with a specific exception.
- Organize by **bounded subsystem responsibilities**, never by programming language alone. See [system catalog](docs/system-overview.md), [16 detailed designs](docs/subsystems/README.md), [architecture](docs/architecture.md) and [contracts](docs/design/contracts.md).
- A logical subsystem is not necessarily a microservice or repository. Keep independent state ownership and typed interfaces even in an embedded single-process simulator.
- The current Rust/Python/TypeScript bootstrap is **not** the target code layout; migration is a separate implementation task.

## Engineering decisions

- Rust for deterministic virtual-time/packet/queue core; Python for orbital/scientific batch models and experiments; TypeScript for console and visualization.
- Use ns-3, SNS3, OpenSAND, OAI, Open5GS, GNU Radio, Linux netns and FRRouting through reviewed adapters where appropriate, not as a claim of common air-interface compatibility. See [dependency policy](docs/dependencies.md).
- Specify whether an experiment is analytical, packet-discrete-event, protocol, network emulation or HIL; do not silently mix fidelity claims or virtual and wall time.
- Each physical measurement requires documented unit, time scale and reference frame; never treat TEME as ECEF.
- Model resources honestly: finite link capacity, queue limits, acquisition time, controller propagation, failure and recovery.
- Preserve deterministic runs (seed, input digests, manifest, code/dependency revision), packet accounting and event causality.
- Every feature requires contract tests, cross-subsystem acceptance evidence, observability, failure cases and performance notes.
- Do not claim work completed unless compiled, tested or externally verified. A design file is not proof that its subsystem exists.
- External dependencies require pinned versions, transitive license review and golden-test comparison before integration.
